The problem

Models guess dates.
The API doesn't.

Support dates move: a release gets extended, a cycle is cut short, a new one ships. A model answering from training data is months behind and sounds just as sure. This server lets it read the date from endoflife.date at the moment you ask.

  • {% include ".icons/material/check-decagram-outline.svg" %} Every call is live: there is no cache to go stale
  • {% include ".icons/material/check-decagram-outline.svg" %} Dates arrive as ISO 8601 with explicit isEol flags
  • {% include ".icons/material/check-decagram-outline.svg" %} A wrong product name returns the right one to try

Three ways to ask

One release, one product,
or the whole catalog.

Your assistant picks the tool that fits the question. Start narrow for a yes or no, go wide to plan an upgrade, and browse when you don't know the name.

One release

"Is Python 3.10 still supported?"

The answer is two fields: whether support has ended, and when.

product_get_cycle python 3.10
→ isEol: true
  eolFrom: 2026-10-01

A whole product

"What should we upgrade to?"

Every release cycle with its dates, newest first, ready to compare.

product_get_all kubernetes
→ 1.37  eol 2027-10-28
